# Operations

## Runtime and ownership

Source assets live together in `wallpaper/`; release packages and the installed Lively project keep those filenames at their root. `wallpaper/grid-wallpaper.html` loads sibling CSS, canonical `grid-config.js`, the Canvas renderer, optional desktop telemetry and native settings bridges, then the settings UI. The runtime makes no internet requests and requires no npm dependencies. The desktop panel ships the official WebView2 SDK libraries and uses the installed Microsoft runtime. GitHub issues track current work; [delivery #1](https://github.com/gagexhill/grid-wallpaper/issues/1) owns laptop acceptance and [privacy #6](https://github.com/gagexhill/grid-wallpaper/issues/6) records the accepted publication review.

`wallpaper/grid-config.js` owns browser defaults, ranges, presets and host link metadata. `scripts/lively-properties.cjs` generates the checked-in native JSON beside it. Lively stores customization per display. The custom desktop window persists through native CLI commands; inline controls in the optional Chromium wallpaper player are session previews because its property callback is one-way. Browser settings use validated local storage; unavailable storage leaves a usable session with an explicit notice.

## Validate

Use the lockfile with `npm ci`, then run one completed command at a time:

```powershell
npm run check
npm run test:browser
npm run test:install
npm run build:settings
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\install.ps1 -Preview
npm run package
```

Node's built-in tests cover lifecycle and settings regressions. Playwright uses installed Edge, one worker and no retries; browser screenshots and traces are ignored runtime evidence under `test-results/`. They prove browser rendering only. Windows PowerShell tests exercise installer functions in isolated temporary fixtures without launching or modifying Lively. `npm run generate` refreshes native properties after canonical configuration changes. `npm run check` fails when the generated JSON drifts.

Development validation stays local; the release-only Actions authorization and preflight are under [GitHub release security](#github-release-security). GitHub-managed Dependabot updates can run despite disabled repository Actions; GitHub documents standard Dependabot jobs as excluded from included Actions minutes. The monthly version-update configuration and native security updates use that managed path. See GitHub's [Dependabot execution and billing documentation](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-on-actions).

## Install, update and remove

The entry command is in README. `install.ps1 -Preview` changes nothing; `-SkipLaunch` prepares/copies files without opening Lively or changing the active wallpaper. The installer honors Lively's native library setting and verifies copied hashes. A successful CLI submission is not evidence that desktop playback rendered correctly.

Run the same installer from a new extracted package to update. It retains Lively's separate saved customization and waits for a readable native library location before copying files. If startup does not finish in time, setup exits with code 2 and can be rerun. `-SkipLaunch` also returns 2 when Lively has not initialized its library yet. Complete Lively's first-run wizard when requested. If WinGet is absent, install/update Microsoft's App Installer, reopen PowerShell, and rerun. If another wallpaper already occupies the intended target, the installer stops instead of overwriting it.

When the thumbnail or metadata changes, setup closes and reopens Lively's library window through native commands so its cached tile updates. The wallpaper core remains running. If the window takes too long to close, reopen it from Lively's tray icon.

README owns the ordered removal steps: first run the extracted package's installer with `-RemoveSettingsLink` to stop the settings helper and remove its per-user registrations, then remove Grid Wallpaper through Lively's library. The first command preserves saved settings; Lively's library deletion also removes that wallpaper's saved customization. The separate local helper profile is retained. Removing the library item alone does not remove its registrations. Uninstall Lively through Windows Installed apps only if it is no longer wanted. There is no custom service, scheduled task, background updater or global execution-policy change to undo.

The installer registers a per-user settings link to the fixed installed `grid-settings.exe --uri` command. Its parser accepts only the canonical scheme, the open action, and bounded normalized button coordinates; it never interprets URI input as a command or filesystem path. A fixed `--warm` command in Windows' per-user Run key prepares the same host after sign-in. Registration preserves unrelated Run values. Run `install.ps1 -RemoveSettingsLink` to stop the helper and remove both owned registrations. Setup writes machine-specific paths only to the installed `windows-host.json`; that file is excluded from source and packages. The host uses a local WebView2 profile under LocalAppData's `Grid Wallpaper` directory. Updates ask it to flush and exit before replacing files.

The custom settings panel supports the primary display in Lively's per-screen layout. It uses the same HTML and controls as browser preview, with a borderless normal window and a 16 DIP working-area margin. The panel's top-right corner aligns with the button's center where the work area permits; native clipping preserves the CSS rounded border. It does not remain always on top. It validates changes against native property metadata, coalesces slider input, calls native `setprop`, and checks the exact saved value before displaying confirmation. Use Lively's native Customize command for other arrangements or the optional Chromium player.

The desktop button uses a small native window with real mouse capture, so a drag continues outside its bounds without starting Explorer's selection rectangle. An open panel follows the button during dragging and edge snapping. Clicking or activating outside the panel and launcher dismisses it; internal controls and owned picker popups retain normal interaction. Its six press-animation frames are rasterized from the existing CSS and SVG by `grid-native-settings.js`; the native host does not own a second theme or glyph. Its snapped side and vertical position are private local preferences in the existing profile. A normal click toggles the warmed panel in the same process; the registered URI remains available for recovery.

Closing hides the panel immediately; it finishes pending saves and suspends WebView2 after a short hidden grace period for quick repeated toggles. Opening reuses that control and refreshes native settings without discarding pending edits. Save failure brings the panel back with an explicit error. When Lively exits, the browser and launcher are disposed. A lightweight supervisor waits for Lively to return, using low-frequency in-process checks while dormant; it never starts Lively. Native configuration notifications retire the controls when Grid is no longer the supported active wallpaper. Follow Microsoft's [WebView2 performance guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance) when changing this lifecycle.

Setup waits up to 15 seconds for the panel to become ready. For diagnostics, the installed helper's `--status` command emits a local JSON snapshot of readiness, visibility, suspension, launcher state, physical window/work-area geometry and telemetry availability/connection/streaming. It omits the session capability and port. `--self-test` checks value validation, telemetry boundaries, URI boundaries and anchor calculations; `--close` flushes and exits the helper for updates. Neither diagnostics command changes wallpaper settings.

Automatic dome readouts use actual rendered base-size multipliers through `grid-live-telemetry.js` and `windows/dome-telemetry.cs`. Global size and display fitting also affect the final drawn radius. Focused sliders edit the saved base and resume live movement on blur. The helper uses .NET Framework's HTTP.sys-backed `HttpListener` and WebSocket APIs with an explicit loopback prefix, local/remote endpoint checks, a session capability, strict frame validation and one producer. It writes a current-user-only `windows-telemetry.js` in the installed folder, rotates it on helper restart, and removes its own session file on exit. This file is excluded from Git and distribution. No URL reservation, firewall rule, separate server setup or additional runtime dependency is installed. Live samples never write Lively settings and are requested at up to 15 fps only while the automatic dome readout is visible. If the connection is unavailable, base controls remain usable with an explicit notice.

To roll back, retain a previously reviewed MIT-licensed release package (preview 5 or later) and rerun its installer. Previews 1–4 used the former author credit; their installers reject the corrected credit on a newer installation. Current setup accepts that exact legacy credit only when the title, runtime filename and project contact still match, then installs the approved author and MIT notice while preserving saved customization. Do not delete the library or host saved settings as a troubleshooting shortcut.

## Native acceptance

Record exact source commit, package SHA256, Windows/Lively versions, display configuration and results in #1. Keep captures local and mark each unperformed check open. Run these steps on the installed copy using the primary display, WebView2 player and per-screen layout:

1. Install from a clean extracted package using the README command. Confirm animation behind desktop icons. From the installed wallpaper folder identified by setup, require exit code 0 from `(Start-Process .\grid-settings.exe -ArgumentList '--self-test' -WindowStyle Hidden -Wait -PassThru).ExitCode`; run `.\grid-settings.exe --status | ConvertFrom-Json` for the diagnostic snapshots below.
2. Open the custom panel with the grid button. Confirm it appears above shortcuts, controls respond, and status reports `ready: true`, `visible: true`, `suspended: false`. Record time from click to interactive controls. Check the button's press feedback, close control and Escape. Toggle the button rapidly five times from closed, then close; after pending work settles, require `visible: false` and `suspended: true`. Reopen and confirm responsive controls.
3. Record a numeric setting, change it, and hide the panel immediately. Wait for suspension, reopen, and verify the new value in both the custom panel and Lively's Customize command. Restore the original value the same way. Fully exit Lively, confirm the browser and launcher disappear while the helper becomes dormant, then relaunch and verify saved values and panel recovery. Select another wallpaper and then Grid again; its button must follow Grid's active lifetime.
4. Move the grid button near the display edges and reopen the panel at each position. Drag quickly beyond the button and release outside it; confirm no desktop selection rectangle or continued movement after release. Compare status window bounds with `screen.workArea`; confirm the working-area margin, button anchor and unobscured bottom controls. Visually check all rounded corners against the CSS shape and confirm another foreground app can cover the panel.
5. Record Lively's startup preference and the relevant per-user registrations locally. Reinstall the same package and verify saved values remain. From the extracted package, run the README installer command with `-RemoveSettingsLink` before removing any library files. Confirm the helper exits and only its owned protocol and Run value disappear. Reinstall and confirm those registrations and quick panel opening return; unrelated Run values and Lively's startup preference must remain unchanged.
6. On the receiving laptop, separately record clean setup, Windows restart/sign-in restoration, sleep/wake, resolution and scaling changes, display hotplug, fullscreen pause, and battery pause/resume under the chosen Lively policies. Repeat panel placement and persistence checks after display changes. Leave any unavailable hardware scenario open; desktop or browser checks do not prove laptop behavior or battery performance.

Native host settings own playback and startup policy. Preserve their original values after acceptance. During the drag check, repeat with the panel already open and confirm that it follows the button; click another app or the desktop to confirm dismissal. Color picker interaction and pending-save completion must remain usable.

For live readouts, expand Domes with automatic sizing enabled and require `telemetry.connected` and `telemetry.streaming`. Confirm changing values match rendered pulses while saved base values stay unchanged. Focus and edit a base, then blur to resume live movement. Freeze/unfreeze and confirm values follow actual playback. Collapse Domes, hide the panel and stop the helper in separate checks; streaming must stop and the bootstrap must disappear after helper exit. Restart the helper and confirm reconnection without restarting the wallpaper. These installed checks are distinct from a browser host mock or parser self-test.

## Packaging and privacy

`wallpaper-files.json` owns the flat runtime filename allowlist used by the installer and packager. `scripts/package.ps1` reads browser assets from `wallpaper/`, native outputs from `dist/settings-host/` and setup/docs from the root, then writes the flat ZIP and SHA256 under ignored `dist/`. The installer resolves both a source checkout and an extracted release through `Get-RuntimeSource`. Packages exclude Git history, developer dependencies, tests, screenshots and local state. The Windows npm packaging command clears only its child process's inherited `PSModulePath`, allowing Windows PowerShell to resolve its own modules when called through npm from PowerShell 7. This addresses Microsoft's [documented module-path inheritance behavior](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_psmodulepath).

Packaging invokes `scripts/build-settings.ps1`. The build pins Microsoft's WebView2 NuGet SDK, verifies its SHA512 against official metadata, and compiles x64 with Windows' .NET Framework compiler. `package.json` owns the product version and description; `wallpaper/LivelyInfo.json` owns its product name and author. The build generates assembly attributes under ignored `dist/` and verifies the compiled executable's metadata. Full semantic versions identify prereleases; numeric file/assembly versions use major.minor.patch.0. Outputs and SDK cache stay under `dist/`; the package contains the helper, three required SDK libraries and the SDK license, with no debug symbols or machine configuration. Root `LICENSE.txt` owns the project's MIT terms; the runtime allowlist carries it into both the ZIP and installed folder alongside the separate `webview2-license.txt`. The receiving machine uses the WebView2 Runtime installed with Lively.

Inspect extracted contents before sharing. The repository is public following the Owner-approved review in #6; rescan changed source, metadata and artifacts before publishing a new release. History rewrites or credential rotation require an exact remediation plan; never copy sensitive values into tracking comments.

`thumbnail.jpg` and `preview.gif` are reviewed runtime assets, generated with `npm run thumbnail` using Edge and the development-only `gifenc` encoder. The renderer uses a seeded Sage preview with higher line contrast for a readable small tile; these preview settings do not change wallpaper defaults. The GIF loops forward and backward at half the original preview playback speed. Lively plays it automatically in normal library mode and uses the still image in lite mode.

Lively's automatic capture belongs to interactive import and is unavailable to this folder-copy setup. Its private bundled image assemblies are not a supported standalone build API. The small generator uses an established JavaScript encoder so regeneration does not depend on an installed Lively directory or another system tool. Regenerate and visually review both assets after material visual changes. Native desktop captures stay ignored and are never included in the package.

## GitHub release security

GitHub owns live access and protection settings. [Security hardening #12](https://github.com/gagexhill/grid-wallpaper/issues/12) records native evidence; this procedure describes the intended policy, not a substitute for rereading it. Only the Owner currently has repository access. Keep unused collaborators, invitations, deploy keys, webhooks, secrets, variables, environments, wiki, Pages and discussions absent or disabled.

The active `Protect main` ruleset requires a pull request, resolved review conversations and zero required approvals so the solo Owner can merge after local validation. It blocks force pushes and branch deletion and has no routine bypass. `Protect version tags` blocks updates and deletion of `v*` tags while allowing new versions. GitHub deletes merged branches automatically. Use the repository's public account handle and GitHub no-reply address for source attribution; prefer a rebase merge to preserve the reviewed author. GitHub rewrites committer information during rebase, so reread both author and committer names/emails after every merge rather than treating the merge method as privacy proof.

The Owner authorizes GitHub Actions for this repository's final production/release work only. Development, pull-request, push-triggered and scheduled validation stays local. Before enabling execution, prepare a manually dispatched release workflow tied to reviewed main-branch source and the canonical package version. Use standard GitHub-hosted runners, explicit timeouts and concurrency, full-SHA action pins, an action allowlist and minimum per-job permissions. Recheck native Actions permissions, workflows, runs and outside-contributor approval before publication. Do not introduce AppVeyor, larger runners or self-hosted runners as substitutes. Signing-provider enrollment and charges still require a separate Owner decision in #19. No release workflow is configured yet; Actions remain disabled pending that setup.

Default workflow tokens are read-only and cannot approve pull requests. Require approval for all outside fork contributors. GitHub does not currently retain a full-SHA pin requirement while Actions are disabled; configure and verify it when enabling the authorized release workflow. Dependency alerts and managed security update PRs are enabled; review updates locally, without automatic merging. GitHub's dependency graph covers the npm manifests but does not discover the WebView2 SDK constant in `scripts/build-settings.ps1`; review that pinned version against Microsoft's release/security information at each native release. A zero-alert result does not establish SDK coverage.

Immutable releases are enabled. Validate locally and build through the selected release procedure, create a **draft** release, attach the complete ZIP and checksum, download and verify them, then publish. The existing local packager produces unsigned artifacts; a signing workflow must sign and verify the owned executable and installer before computing the final checksum, preserving vendor files and notices. Do not rerun packaging after signing because it recompiles the helper. Published assets cannot be replaced and the tag cannot move. The release itself can still be deleted, but its version tag name cannot be reused; immutability is not a backup. Edit release notes only when needed. GitHub also made previews 2 and 3 immutable when their release metadata was reconciled after the approved attribution rewrite; their file assets did not change. Earlier releases require checking their native `immutable` flag rather than inferring it from the repository setting. Do not replace an existing version's contents. See GitHub's [immutable release behavior](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases).

Keep the Owner account protected with two-factor authentication and secured recovery methods. The Owner attested these controls during #6's accepted public-transition review; repository APIs do not establish account authentication posture, and a registered passkey alone does not establish whether password-only access remains possible. Keep credentials and recovery codes out of repository evidence. A public repository exposes its account handle, contribution history, license notices and readable GitHub profile; a history rewrite cannot make the owning account anonymous.

Keep native secret scanning, **repository-level** push protection and private vulnerability reporting enabled. These controls became available and were verified when the Owner authorized public visibility. Before publication, reread them alongside the active branch/tag rules, Actions scope/settings, contributor approval, dependency alerts, access list and release assets. Record any rejected or unavailable setting in the security tracker instead of claiming it is enabled. Local secret scans remain required; native scanning does not replace artifact inspection. GitHub documents [secret scanning availability](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning), [push protection](https://docs.github.com/en/code-security/concepts/secret-security/push-protection) and [private reporting](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository).

Public forks cannot be prohibited by a repository setting. Treat public issues and pull requests as untrusted input: inspect diffs without running contributed code, and do not expose local credentials or authorize workflows merely to validate a contribution. [SECURITY.md](https://github.com/gagexhill/grid-wallpaper/blob/main/.github/SECURITY.md) owns vulnerability-reporting instructions; public reports must never contain exploit secrets or personal information.

## Host selection

Windows' documented desktop-wallpaper API manages images/slideshows; it is not a Canvas host. Lively is the selected maintained host because it supports HTML, persistent native properties, pause events, WinGet installation and laptop policies without a paid dependency. Wallpaper Engine supports web wallpapers and similar pause policies but adds a purchase/distribution dependency and offers no demonstrated advantage for this renderer.

The small installer adapter is needed because stable Lively `setwp` accepts project folders inside its configured library, while its media importer does not import raw HTML projects. It reads native settings, copies an allowlisted project, and invokes native commands; it does not duplicate the host. Replace that copy step when a reliable native arbitrary-project import command becomes available.

Windows places the wallpaper below desktop shortcuts, so CSS stacking cannot lift a panel above them. Lively's WebView2 player sends user-opened links to Windows, and its generated native editor does not preserve this custom UI. Its forwarded wallpaper mouse input also leaves Explorer handling the physical desktop click. A small window built on Microsoft's official WebView2 WinForms SDK covers the custom-panel gap; a shell-owned native launcher captures dragging and opens that panel directly. Neither window stays topmost. The adapter allows only installed local assets, validates message origin/properties/values, and retains Lively's persistence. Remove it if Lively provides reliable native hosting and input for the existing panel above icons. The integration follows Microsoft's [WinForms WebView2 guide](https://learn.microsoft.com/en-us/microsoft-edge/webview2/get-started/winforms) and [owned-window rules](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features).

Lively's property callbacks deliver configuration to the wallpaper; they do not return live simulation values to another window. Native `setprop` changes persisted configuration, so it cannot carry per-frame readouts. The limited loopback adapter fills this gap using the platform's [HttpListener](https://learn.microsoft.com/en-us/dotnet/api/system.net.httplistener) and [WebSocket](https://learn.microsoft.com/en-us/dotnet/api/system.net.websockets.websocket) APIs. Replace it if the host adds a supported return channel for live wallpaper state.

Lively 2.2.1 maps local files to a folder-derived virtual HTTPS origin. The bridge accepts only that exact installation origin or the legacy file origin, alongside its session authentication. Its address derivation follows the installed release's [local navigation](https://github.com/rocksdanister/lively/blob/v2.2.1.0/src/Lively/Lively.Player.WebView2/Extensions/WebView2/CoreWebView2Extensions.cs) and [stable hostname](https://github.com/rocksdanister/lively/blob/v2.2.1.0/src/Lively/Lively.Common/Helpers/LinkUtil.cs) implementation; it does not allow arbitrary localhost origins.
